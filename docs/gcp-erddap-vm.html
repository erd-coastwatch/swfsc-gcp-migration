ERDDAP VM Setup

This section describes the initialization and configuration of a dedicated ERDDAP serving environment after its infrastructure has been deployed. Size the VM and disks for the workload: a local-data ERDDAP may need a high-memory VM, a multi-terabyte cache disk, and a GCS data bucket, while a mostly remote-data ERDDAP can often use a smaller VM and disk without a dedicated bucket.

The similarly named storage components have different purposes:

Component Terraform or documentation name Purpose
Boot disk YOUR_ERDDAP_BOOT_DISK_NAME Operating system, Java, Tomcat, ERDDAP application, and configuration
Persistent data disk YOUR_ERDDAP_DATA_DISK_NAME ERDDAP working directory, logs, decompressed files, and rclone cache; survives VM rebuilds
ERDDAP data bucket YOUR_ERDDAP_BUCKET_NAME Source datasets mounted read-only into the VM; optional for a remote-only catalog
Processing/data bucket YOUR_PROCESSING_OR_DATA_BUCKET_NAME Inputs or outputs for processing workflows; not necessarily mounted by ERDDAP
Bucket mount /mnt/gcs/erd Read-only filesystem view of the ERDDAP data bucket
Persistent mount /mnt/disks/erddap-data Filesystem mount for the attached data disk

The example names are placeholders. Keep the selected resource names consistent between Terraform, rclone, /etc/fstab, and the commands below.

1. Configure the Operating System Environment

1.1 Configure Shared User Group Permissions

Create a shared group for operational data access and add the required users. YOUR_OPERATIONAL_USERNAME is the normal Linux account used by an operator or automation process to administer data outside Tomcat. If no separate account is required, omit that line and use only your login plus the tomcat service account created by the installer.

getent group cwatch >/dev/null || sudo groupadd cwatch
sudo usermod -aG cwatch $USER                     # Add your current user
sudo usermod -aG cwatch YOUR_OPERATIONAL_USERNAME # Add the operational/service account (e.g. erd)
newgrp cwatch                                     # Refresh group membership (or log out and back in)

1.2 Initialize and Mount the Persistent Data Disk

Before formatting or mounting the persistent data disk, determine whether the disk is new or reattached from an existing deployment. If the disk was attached from a previous VM, do not reformat it.

# Identify the attached disk
ls -l /dev/disk/by-id/

# Check whether the disk already contains a filesystem
sudo blkid /dev/disk/by-id/google-erddap-data

# If no filesystem exists, create one
sudo mkfs.ext4 -m 0 -E lazy_itable_init=0,lazy_journal_init=0,discard \
    /dev/disk/by-id/google-erddap-data

# Create mount point and mount the disk
sudo mkdir -p /mnt/disks/erddap-data
sudo mount -o discard,defaults \
    /dev/disk/by-id/google-erddap-data \
    /mnt/disks/erddap-data

# Make the mount persistent across VM reboots
disk_uuid=$(sudo blkid -s UUID -o value \
    /dev/disk/by-id/google-erddap-data)
test -n "$disk_uuid" || {
  echo "Unable to determine the data-disk UUID" >&2
  exit 1
}

sudo cp -a /etc/fstab "/etc/fstab.before-erddap-$(date +%Y%m%d-%H%M%S)"
if ! grep -qE "^[[:space:]]*UUID=${disk_uuid}[[:space:]]" /etc/fstab; then
  echo "UUID=${disk_uuid} /mnt/disks/erddap-data ext4 defaults,discard,nofail 0 2" |
    sudo tee -a /etc/fstab
fi

# Set permissions for the shared cwatch group
sudo chown root:cwatch /mnt/disks
sudo chmod 2775 /mnt/disks
sudo chown root:cwatch /mnt/disks/erddap-data
sudo chmod 2775 /mnt/disks/erddap-data

# Optional: standard symlink used by operational workflows
sudo test -e /data || sudo ln -s /mnt/disks/erddap-data /data

Verify every directory in the path is traversable by cwatch members. Correct permissions on the mount itself are insufficient if /mnt/disks remains 0700 root:root.

namei -l /mnt/disks/erddap-data
findmnt /mnt/disks/erddap-data
df -hT /mnt/disks/erddap-data

# Validate the fstab entry before rebooting
sudo umount /mnt/disks/erddap-data
sudo mount -a
findmnt /mnt/disks/erddap-data

1.3 Configure GCS Connectivity with Rclone

Rclone is used to mount GCS buckets directly into the ERDDAP VM filesystem using a Virtual File System (VFS) mount. The persistent high-speed data disk acts as a local VFS cache to improve ERDDAP performance when serving large NetCDF datasets from cloud storage.

Install rclone:

curl -fsSL https://rclone.org/install.sh | sudo bash

Permit FUSE mounts to use rclone’s --allow-other option:

if ! sudo grep -qx 'user_allow_other' /etc/fuse.conf; then
  echo user_allow_other | sudo tee -a /etc/fuse.conf
fi

Create a shared rclone configuration:

sudo mkdir -p /home/YOUR_OPERATIONAL_USERNAME/rclone/

sudo tee /home/YOUR_OPERATIONAL_USERNAME/rclone/rclone.conf > /dev/null <<EOF
[gcs-remote]
type = google cloud storage
env_auth = true
project_number = YOUR_GCP_PROJECT_NUMBER
location = YOUR_GCP_REGION
EOF

sudo chown -R root:cwatch /home/YOUR_OPERATIONAL_USERNAME/rclone/

Create the local cache and mount directories before starting the service:

sudo mkdir -p /mnt/gcs/erd
sudo mkdir -p /mnt/disks/erddap-data/rclone-cache
sudo chown root:cwatch /mnt/gcs /mnt/gcs/erd
sudo chmod 2775 /mnt/gcs /mnt/gcs/erd

Then create the systemd persistence service:

# Choose a cache limit that leaves free space for ERDDAP's working files and
# logs. For example, use 100G on a 250G disk or 2000G on a 4TB disk.
RCLONE_CACHE_MAX_SIZE=100G

FUSERMOUNT_BIN=$(command -v fusermount3 || command -v fusermount)
test -n "$FUSERMOUNT_BIN" || {
  echo "fusermount is not installed" >&2
  exit 1
}

sudo tee /etc/systemd/system/rclone-mount.service > /dev/null <<EOF
[Unit]
Description=Rclone High-Performance GCS Mount
After=network-online.target
Wants=network-online.target
RequiresMountsFor=/mnt/disks/erddap-data

[Service]
Type=notify
User=root

ExecStart=/usr/bin/rclone mount gcs-remote:YOUR_ERDDAP_BUCKET_NAME /mnt/gcs/erd \
    --config /home/YOUR_OPERATIONAL_USERNAME/rclone/rclone.conf \
    --allow-other \
    --read-only \
    --dir-cache-time 1h \
    --attr-timeout 1m \
    --vfs-cache-mode full \
    --vfs-cache-max-age 48h \
    --vfs-cache-max-size ${RCLONE_CACHE_MAX_SIZE} \
    --vfs-cache-poll-interval 1m \
    --cache-dir /mnt/disks/erddap-data/rclone-cache \
    --buffer-size 128M \
    --vfs-read-ahead 256M \
    --vfs-read-chunk-size 64M \
    --vfs-read-chunk-size-limit 2G \
    --dir-perms 0775 \
    --file-perms 0775 \
    --gid $(getent group cwatch | cut -d: -f3) \
    --umask 002 \
    --rc \
    --rc-no-auth

ExecStop=${FUSERMOUNT_BIN} -u /mnt/gcs/erd
Restart=on-failure
RestartSec=10

[Install]
WantedBy=multi-user.target
EOF

Key rclone mount notes:

  • --read-only prevents accidental modification of cloud-hosted datasets.
  • --vfs-cache-mode full enables local caching on the persistent disk.
  • --vfs-cache-max-size must remain comfortably below the persistent disk’s available capacity so ERDDAP working files and logs cannot be crowded out.
  • --vfs-read-ahead improves sequential read performance for ERDDAP requests.
  • --attr-timeout 1m helps rclone detect when NRT files are replaced by science-quality versions in GCS.
  • --dir-cache-time 1h means a newly created cloud directory might not appear through the mounted filesystem for up to an hour unless the VFS directory cache is refreshed.
  • --rc starts rclone’s localhost-only remote-control endpoint. --rc-no-auth is acceptable only because the endpoint remains bound to localhost and is protected by the VM.

Enable and start the service:

sudo systemctl daemon-reload
sudo systemctl enable rclone-mount.service
sudo systemctl start rclone-mount.service

Verify the mount and cache status:

ls -l /mnt/gcs/erd       # Confirm GCS bucket contents are visible
rclone rc vfs/stats      # Monitor cache usage and read-ahead status

After adding or replacing objects directly in GCS, refresh the mounted directory cache when the files must become visible immediately:

rclone rc vfs/refresh recursive=true

For a very large bucket, refresh only the affected directory when possible because a recursive refresh can take a long time:

rclone rc vfs/refresh dir=PATH/RELATIVE/TO/BUCKET recursive=true
Tip

Storage capacity: The configured cache size is a managed ceiling. Rclone automatically purges the oldest cached data when it reaches this limit. Set the limit below the persistent disk’s available capacity so ERDDAP working files and logs retain adequate space.

NRT updates: By checking attributes once per minute, the system will automatically fetch the updated science-quality version of a file even if the filename has not changed.

2. Install and Configure ERDDAP

2.1 Run the SWFSC ERDDAP Installation Script

The public installation script installs pinned versions of Java, Tomcat, ERDDAP, and the required system dependencies. It also configures the tomcat-erddap systemd service, ERDDAP’s persistent working directory, and Tomcat’s reverse-proxy handling. Pinning prevents an untested upstream release from silently changing an installation; review and test the script whenever an ERDDAP version is updated.

wget -O erddap_setup.sh \
  https://raw.githubusercontent.com/erd-coastwatch/swfsc-gcp-migration/main/scripts/erddap/erddap_setup.sh

chmod 700 erddap_setup.sh
bash -n erddap_setup.sh
./erddap_setup.sh

The installer enables the tomcat-erddap service but does not start it. This allows setup.xml and datasets.xml to be configured before ERDDAP begins loading datasets.

The installer refuses to overwrite an existing Java or Tomcat installation. ERDDAP upgrades should be performed as a separate, planned operation.

Review the versions that will be installed without modifying the host:

./erddap_setup.sh --help

2.2 Configure ERDDAP

Review and update the ERDDAP configuration. Follow the official ERDDAP installation documentation and, at minimum, verify:

  • bigParentDirectory
  • baseUrl and baseHttpsUrl
  • administrator name, institution, address, phone, and email
  • outbound email settings, or intentionally disabled email settings for staging
  • flagKeyKey
  • subscription and authentication settings
  • the intended datasetsRegex and datasets.xml
sudoedit /usr/local/tomcat_erddap/content/erddap/setup.xml
sudoedit /usr/local/tomcat_erddap/content/erddap/datasets.xml

When ERDDAP is behind an HTTPS load balancer, both public URL values should use the externally visible hostname. This prevents mixed-content failures where an HTTPS page tries to load CSS and images over HTTP.

<baseUrl>https://YOUR_ERDDAP_HOSTNAME</baseUrl>
<baseHttpsUrl>https://YOUR_ERDDAP_HOSTNAME</baseHttpsUrl>

The installer adds a Tomcat RemoteIpValve so Tomcat honors the load balancer’s X-Forwarded-For and X-Forwarded-Proto headers:

<Valve className="org.apache.catalina.valves.RemoteIpValve"
       remoteIpHeader="X-Forwarded-For"
       protocolHeader="X-Forwarded-Proto"
       protocolHeaderHttpsValue="https" />

The default persistent working directory is:

/mnt/disks/erddap-data/erddap/

Confirm the configuration file permissions:

sudo chown tomcat:cwatch \
  /usr/local/tomcat_erddap/content/erddap/setup.xml \
  /usr/local/tomcat_erddap/content/erddap/datasets.xml

sudo chmod 640 \
  /usr/local/tomcat_erddap/content/erddap/setup.xml \
  /usr/local/tomcat_erddap/content/erddap/datasets.xml

Validate the XML before starting ERDDAP:

sudo xmllint --noout /usr/local/tomcat_erddap/content/erddap/setup.xml
sudo xmllint --noout /usr/local/tomcat_erddap/content/erddap/datasets.xml
sudo xmllint --noout /usr/local/tomcat_erddap/conf/server.xml

3. Configure Load-Balancer Firewall Access

A Google Cloud regional internal Application Load Balancer requires ingress to the backend port from both Google’s health-check ranges and the region’s proxy-only subnet. Determine the proxy-only range rather than copying a range from another project:

gcloud compute networks subnets list \
  --project=YOUR_GCP_PROJECT_ID \
  --filter='purpose=REGIONAL_MANAGED_PROXY' \
  --format='table(name,region,network,ipCidrRange,purpose,role)'

Create narrowly scoped VPC firewall rules for TCP 8080. If organizational policy allows destination ranges in VPC firewall rules, restrict these rules to the backend VM addresses.

gcloud compute firewall-rules create allow-erddap-lb-health-checks \
  --project=YOUR_GCP_PROJECT_ID \
  --network=YOUR_NETWORK \
  --direction=INGRESS \
  --action=ALLOW \
  --rules=tcp:8080 \
  --source-ranges=130.211.0.0/22,35.191.0.0/16 \
  --destination-ranges=YOUR_ERDDAP_BACKEND_IPS

gcloud compute firewall-rules create allow-erddap-lb-proxy-ingress \
  --project=YOUR_GCP_PROJECT_ID \
  --network=YOUR_NETWORK \
  --direction=INGRESS \
  --action=ALLOW \
  --rules=tcp:8080 \
  --source-ranges=YOUR_PROXY_ONLY_SUBNET \
  --destination-ranges=YOUR_ERDDAP_BACKEND_IPS

NOAA VM images may also enable Ubuntu’s Uncomplicated Firewall (UFW). Allow the same sources locally, replacing the destination address and proxy range:

sudo ufw allow proto tcp from 130.211.0.0/22 \
  to YOUR_ERDDAP_INTERNAL_IP port 8080 comment 'Google LB health checks'

sudo ufw allow proto tcp from 35.191.0.0/16 \
  to YOUR_ERDDAP_INTERNAL_IP port 8080 comment 'Google LB health checks'

sudo ufw allow proto tcp from YOUR_PROXY_ONLY_SUBNET \
  to YOUR_ERDDAP_INTERNAL_IP port 8080 comment 'Regional LB proxy subnet'

sudo ufw status numbered

Do not expose port 8080 to the public internet. The load balancer terminates HTTPS and connects to Tomcat on the private backend address.

4. Start and Verify ERDDAP

sudo systemctl start tomcat-erddap
sudo systemctl --no-pager --full status tomcat-erddap

curl -fsSI http://127.0.0.1:8080/erddap/status.html
curl -fsSI http://YOUR_ERDDAP_INTERNAL_IP:8080/erddap/status.html

Follow the service log during the initial dataset load:

sudo journalctl -u tomcat-erddap -f

Follow dataset construction in ERDDAP’s application log:

log=/mnt/disks/erddap-data/erddap/logs/log.txt

sudo tail -F "$log" |
grep --line-buffered -E \
  'constructing EDD|constructor finished|LoadDatasets.run finished|failed to load|ERROR:|Exception'

From Cloud Shell, confirm that the load balancer considers the backend healthy:

gcloud compute backend-services get-health YOUR_BACKEND_SERVICE \
  --project=YOUR_GCP_PROJECT_ID \
  --region=YOUR_GCP_REGION

Confirm the external route and generated HTTPS assets:

curl -kfsSI https://YOUR_ERDDAP_HOSTNAME/erddap/status.html

curl -kfsS https://YOUR_ERDDAP_HOSTNAME/erddap/index.html |
grep -oE '<link[^>]*erddap2.css[^>]*>'

The backend must report HEALTHY, the status request must return HTTP 200, and the CSS URL must begin with https://YOUR_ERDDAP_HOSTNAME/. Use -k only for a staging certificate that is not yet trusted; production clients should validate the complete certificate chain.

Stop or restart ERDDAP with:

sudo systemctl stop tomcat-erddap
sudo systemctl restart tomcat-erddap
